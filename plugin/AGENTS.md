# AGENTS.md — DeepCluster

DeepCluster implementation work follows the repository instructions. This page guides agents that use it to delegate tasks. Read [README.md](README.md) for setup and [the design reference](docs/design.md) for scheduling, write-claim, and evidence limits.

## Install the entry point

Install the shipped `/DeepCluster` skill from the package's `dsh` profile: `dsh --profile deep-cluster install --skills-root <absolute-skills-dir>` writes `<skills-root>/<commandName>/SKILL.md` and prints it. `--label <name>` names the controlling harness. Presets remain `--planner cursor`, `--planner codex`, or `--planner all`; `--skills-root` and `--planner` conflict, and `--label` requires `--skills-root`. Installation preserves the saved endpoints, `dshPath`, and dashboard roots in `~/.deep-cluster/config.json` and an existing installed skill. Launch the API and dashboard only through supported `dsh` profiles; the service keeps its own state under `<dshPath>/.deep-cluster/service-state/`, and `dshPath` is required. The persistent service lifecycle is Windows only; elsewhere run them under your own supervisor. A WSL-launched Linux descendant is outside the Windows process range, so its exit cannot be confirmed.

The API admits requests from this computer without credentials. It rejects non-loopback peers with 403 `remote-peer`, browser-origin requests, and a non-loopback Host header. There is no bearer token: the token file, `--api-token-file`, `apiTokenFile`, and `DEEPCLUSTER_API_TOKEN_FILE` are retired, and a saved `apiTokenFile` in `~/.deep-cluster/config.json` fails loud and must be deleted. The dashboard keeps the DSH Web login URL from `service login-url`. Both scheduled tasks run hidden through `conhost.exe --headless`, start and keep running on battery, and have no execution time limit.

## Delegate bounded work

Use the installed `/DeepCluster` skill explicitly, or delegate routine work proactively when its output can be checked independently. Suitable tasks include focused implementation, tests, data collection, and profiler analysis. The controlling agent owns design decisions, task scope, final integration, and truthful reporting.

Read the workspace instructions and previous task examples before writing a plan. A ledger pass is a worker report, not a capability guarantee. Compare similar tasks, tools, models, and hardware; inspect failures as well as successes.

## Write and run the plan

Use `## Step <id>: <title>`, a specialist `role`, and an `acceptance:` bullet list with concrete checks. Keep instructions below the metadata. Give each worker a bounded responsibility and named artifacts.

Missing `depends_on` keeps steps sequential. Declare `depends_on: none` only for independent tasks; otherwise list prerequisite ids. Missing `access` reserves the whole physical worktree exclusively. Use `access: read-only` for no source writes and no write claim, or `access: write` with `writes:` listing literal repository-relative paths (a trailing `/` covers descendants). Globs, absolute or drive-qualified paths, UNC paths, backslashes, `..` or `.` segments, `.git`, `.deep-cluster`, reserved Windows names, and symlink or junction escapes outside the worktree are rejected. `resources` add exact-name locks and never replace the write claim; `resources: none` does not opt out (use `access: read-only`). `git: write` requires whole-worktree access, a real Git worktree, and the shared common-directory lock. Use `dependency_policy: settled` only for a diagnostic reviewer or tester that must run after a failed prerequisite; it never turns a failed run green. `supervisor` is reserved and cannot be a step id. DeepCluster never commits, resets, stashes, cleans, or rebases; workers must preserve the recorded branch, HEAD, and dirty/untracked state. One snapshot reads `git status --untracked-files=all` and `git ls-files --stage`, hashes pre-existing changes and claimed files, and compares staged-entry content identity; a clean file changed and restored between snapshots, ignored/generated files, and shell writes outside a claim are not detectable. Claims conflict by canonical absolute path across parent/child workspaces, nested repositories, and an outside non-Git ancestor; a held claim-registry mutex is never taken over automatically. The first submission creates the workspace's `.deep-cluster/` (journal, team mailboxes, plan files) with a `.gitignore` containing `*`, so it needs no repository ignore rule.

Use the dedicated local HTTP API for every task operation, including observation and acknowledgements. Read the installed skill's saved endpoint and DSH path. If neither is known, ask the user for an endpoint or a DSH checkout containing the plugin, then save the verified connection. Submit the plan file in one `POST /v1/runs` request: a `text/markdown` or `text/plain` body with `workspace`, `maxConcurrency`, `timeoutMs`, `maxAttempts`, and `maxRepairs` in the query, or the JSON body `{workspace, plans, ...}` with no query options; `POST /v1/plans/validate` accepts the same bodies. Send an `Idempotency-Key` to make retries safe; `wait=<seconds>` holds the response until the run settles or the wait ends, and `view=report` returns the compact report. `GET /v1/runs/:id` accepts `wait` and `view`; `POST /v1/runs/:id/cancel` accepts `view`. When a request cannot connect, any agent, including a delegated worker, may run `service start` once; it is idempotent and concurrent callers serialize. Startup and interrupted-controller recovery follow the safeguards in the README persistent-service section. Set concurrency explicitly when tasks can overlap. Workers use full access with sandboxing disabled.

For a persistent conversation, create an assignment through `/v1/sessions` and submit its exact `{id,generation}` with one plan step in the assigned workspace and role; native turns use one attempt and no repair. Replacement fences old work and requires confirmed teardown or exact settled-generation recovery evidence before creating a fresh native Session with only the explicit handoff. Queue only supervisor-authored fixed runs through `/v1/wakeups`; time or retained-operation triggers do not authorize new allocation or replanning. Host policy hooks may refuse admission or tools, never enlarge permissions or claims. Follow the [session, wakeup, and policy guide](README.md#continue-or-replace-a-worker) for request fields and failure handling.

Declare hardware for every GPU operation, including correctness tests, sanitizers, and measurements. For CPU-only review of saved profiler reports, use `hardware: none`. Use consistent device names and one shared lease root. Do not leave detached GPU work running after a task returns. Expired or dead-owner leases require confirmed process termination before recovery.

## Verify and report

Workers must repeat each acceptance label with an affirmative result and concrete command or measurement evidence. A zero process exit alone does not pass the task. Schedule independent tester and reviewer tasks after implementation; inspect actual artifacts and outputs.

Inspect the API's journal and ledger endpoints for attempts, failures, blocked tasks, leases, and observed activity; use run-scoped cursors instead of repeated tail scans, and read `GET /v1/ledger?tail=N` for the newest N task outcomes. A `view=report` response carries `operationId`, `status`, `error` (`code: message` or null), `steps`, `open`, and `failure`; each step has `id`, `role`, `status`, `attempts`, `summary`, and when present `checks` (acceptance label with worker evidence), `changed` (paths the audit saw change during the step), `auditProblem`, and `improvisation`. `open` lists unresolved improvisation ids, and `failure` carries `stepId` and the last 4,000 characters of the failing output. `POST /v1/ack` settles a `needs-ack` run once its last open improvisation is resolved: `completed`, or `failed` with code `improvisation-rejected` when any was rejected. Update the plan after resolving a deviation, reuse the submission's idempotency key when its outcome is uncertain, and do not silently create duplicate work or lower acceptance to manufacture success.

Write claims coordinate cooperating DeepCluster processes, not the operating system. Arbitrary shell writes can leave a claim, and a failed claim or snapshot check is reported, never converted into a pass.

On first service use, read `service login-url` and show the fresh URL to the user, then open it in a browser and confirm the rendered panel. Never print, store, or send the tokenized dashboard URL outside chat and its private per-run file. Reuse the saved owner, master directory, and lease root. Stopping the dashboard ends its scheduled task, then terminates the recorded dashboard process tree after re-verifying its PID and start time. Automatic startup recovers only machine-proven idle owners. For uncertain or older state, before `service recover`, run `service recover --dry-run` and confirm the exact diagnosed owner and that its workers are gone; `service recover --confirm-lock-owner <owner>` records an operator-confirmed, not machine-proven, recovery. Recovery renames the lock and never replays work or rewrites state. A run whose cancellation reports `cleanup-unconfirmed` keeps its leases quarantined and blocks graceful stop until the operator verifies and terminates the process range and passes `--confirm-cleanup-unconfirmed`.

Failures never authorize broader permissions. Diagnose the failing layer under the configured policy. Unknown descendant cleanup retains ownership and stops new dispatch in that run. Startup preserves known affected scopes so conflicting work remains blocked; unknown scope sets health `recoveryIssues[].blocksAdmission` and refuses all fresh admission while inspection remains available. Preserve evidence and use supported recovery; never relabel uncertain ownership as free.

For GPU performance, state device, precision, dense versus sparse operations, matrix dimensions, clocks, correctness tolerance, warmup, timing method, and measured throughput. Tensor-pipe active percentage and percentage of cuBLAS are different from percentage of theoretical tensor peak.

Attribute work to DeepCluster only when its workers actually performed it. Report unresolved limits and measured outcomes without inventing successful benchmarks.
